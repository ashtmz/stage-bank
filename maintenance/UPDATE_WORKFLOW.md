# 月次更新の手順

対象: `/Users/tmz/Set/Git/Utilitys/stage bank`。毎月1日9:00（Asia/Tokyo）に、このチャットの定期タスクから実行する。

## 調査

1. `src/data/schema.md`、`WATCHLIST.md`、`src/content/update-status.json`、直近の `docs/updates/README.md` と更新記録を読む。
2. 前回の確認日から今回までのメーカー公式発表、正式リリースノート、公開マニュアル、規格団体・劇場・大学の資料を調べる。既存の出典が移転・更新されていれば現在の一次資料を確認する。
3. 舞台、音響、照明、映像・制御、制作、安全、衣裳・メイク、楽器・音楽、電源・通信の不足と変更を確認する。新製品の広告だけに偏らず、既存機器の新機能、相互運用条件、規格改訂、用語の誤りも対象にする。
4. 正式提供と発表・予告、発表日と資料の確認日、機種共通機能と特定バージョンの機能を区別する。既存製品が公式ページに掲載されていることだけを理由に新製品と呼ばない。発売日が確認できない場合は発表日を推測しない。

## 編集

- `src/data/*.json` の用語を更新する。既存 ID は保持する。単なる別名は aliases にまとめ、件数のための重複を作らない。
- 新項目には意味、詳しい説明、使う場面、混同しやすい点、実際に確認した一次資料を付ける。原文の大量転載や、既存用語の名を差し替えただけの説明は避ける。
- 小分類は既存の内容別分類を優先する。同じ話題を「基本／詳細」で分割せず、機材・機能の違いは種類フィルターも使う。統合・移動した分類はインデックスの変更項目に残す。
- `kind` は term / technology / equipment / feature の役割で分類する。機材・固有機能には `verifiedAt` を記録し、確認できたメーカーや版、主要な仕様を載せる。
- 法的要件・周波数・荷重・電源・レーザー・高所作業などの具体的な数値や運用条件を一般化しない。用語説明と操作手順は分ける。
- ブラウザの保存データ、ユーザーが追加した用語、メモ、ブックマークは変更しない。
- `maintenance/checks/YYYY-MM-DD.md` に実際に調べた範囲、公式資料、変更の有無と未確認事項を短く記録する。調査が完了した場合だけ `src/content/update-status.json` の lastCheckedAt を日本時間の日付で更新する。スケジュール設定は維持する。

## 検証と更新インデックス

1. `npm run check:data`、`npm test`、`npm run build` を実行し、不整合を修正する。
2. 内容の変更がある場合は `npm run index:update -- --title '月次更新' --summary '実際の追加・修正点の要約'` を実行する。
3. 自動生成された `src/content/updates.json`、`docs/updates/YYYY-MM-DD-NN.md`、`docs/updates/README.md` を確認する。追加・変更・整理の区分、実際の件数、変更項目、用語 ID、参照資料が差分と一致していることを確認する。スナップショットは `maintenance/content-snapshot.json`。
4. `npm run build` を再実行し、用語画面と更新インデックスのリンクをブラウザで確認する。更新インデックスから現行用語を開けることを確かめる。
5. 内容の変更がなければ空の更新インデックスを作らない。確認日の変更だけでも更新件数を増やさない。

インデックスは実際の意味・説明・仕様・出典などの変化から生成する。過去のインデックスを最新の説明へ書き換えず、当時の内容を残す。名称変更は同じ ID の変更として記録する。整理された項目も過去の索引に残る。

## 通知

意味のある追加・修正ができたときは、件数と変更点、更新インデックスの場所をこのチャットへ通知する。失敗や利用者の対応が必要な場合も通知する。内容の変わらない定期確認では通知しない。

この更新はローカルフォルダで行うため、実行時には対象の Mac と Codex アプリが稼働し、フォルダとウェブ調査が利用できる必要がある。
